# M2 — WebApp de lugares salvos

M2 transforma o backend M1 em um produto web utilizável. O objetivo não é
escalar infraestrutura: é validar que uma pessoa consegue descobrir, revisar e
salvar um lugar com segurança e custo previsível.

## Definition of done

Um visitante consegue abrir o WebApp, receber uma identidade de navegador
privada, submeter uma URL TikTok pública, entender o resultado, confirmar um
local verificado e vê-lo em sua biblioteca. Repetir a URL não repete uma chamada
paga quando o cache já possui a análise compatível.

O M2 termina com um fluxo E2E autenticado no Railway e métricas suficientes
para decidir se um worker, fila ou uma conta recuperável realmente são
necessários.

## Decisões adotadas

- **Runtime:** Next.js App Router e as rotas HTTP existentes permanecem no mesmo
  serviço Railway. PostgreSQL continua o único banco.
- **Identidade inicial:** uma sessão opaca, aleatória e `HttpOnly` cria um
  usuário anônimo por navegador. Não há senha, provedor OAuth ou e-mail nesta
  fase; recuperação de conta é uma decisão posterior, não uma implementação
  parcial de autenticação.
- **Autorização:** o servidor deriva o usuário da sessão. O browser nunca envia
  `userId`, `SAVEPLACE_OWNER_ID`, `API_TOKEN` ou credenciais de provedores. Até
  M2.7, `API_TOKEN` permanece somente como gate operacional da API direta para
  não expor chamadas pagas sem limite.
- **Cache:** fontes, análises e lugares verificados podem ser compartilhados;
  vínculos de análise, idempotência e biblioteca são privados por usuário.
- **TypeSafe:** um julgamento opcional e tipado de suporte entre evidência e
  candidato entra somente após a fundação de produto. Ele nunca verifica um
  endereço, autoriza uma ação ou salva um lugar.

O racional permanece nesta página para que a documentação pública não dependa
dos ADRs privados em `docs/adr/`.

## Modelo de dados alvo

`users` deixa de representar o owner estático. M2.1 introduz `sessions` com um
token opaco armazenado apenas como hash e associado a `users.id`. M2.2 introduz
`user_analyses`, que relaciona uma análise cacheada ao usuário que a solicitou.

```text
users 1---N sessions
users 1---N user_analyses N---1 source_analyses
users 1---N idempotency_operations
users 1---N user_places N---1 places
```

O cache de `source_analyses` permanece global por URL canônica, versão de
pipeline e fingerprint de provedor. Acesso a um `analysisId` de outro usuário
retorna ausência, não detalhes.

## Contratos de produto previstos

Depois de M2.1, requests de produto usam a sessão do cookie. `API_TOKEN` não
é autenticação de browser e permanece apenas como gate operacional temporário
até M2.7. `PROBE_TOKEN` permanece exclusivamente
para o probe operacional fixo.

| Rota | Mudança M2 |
| --- | --- |
| `POST /v1/analyses` | Usuário vem da sessão; exige `Idempotency-Key`. |
| `GET /v1/analyses/:id` | Novo; retorna somente análise vinculada ao usuário atual. |
| `POST /v1/analyses/:analysisId/places/:placeId/save` | Mantém confirmação explícita e exige usuário da sessão. |
| `GET /v1/places` | Lista apenas a biblioteca da sessão. |
| `PATCH /v1/places/:userPlaceId` | Novo; atualiza status, favorito ou nota do usuário da sessão. |
| `DELETE /v1/places/:userPlaceId` | Novo; remove somente o vínculo do usuário, nunca o local global. |

## Guardrails TypeSafe

O sinal TypeSafe recebe apenas `candidate` e `Evidence[]` permitida pelo
pipeline. A pergunta é uma escolha fechada: a evidência suporta o candidato,
é ambígua, ou não o suporta. O código mantém a resposta tipada, distribuição de
probabilidades e confidence, e usa um limiar conservador inicialmente.

- Confidence baixa vira `ambiguous` para UI e revisão, não uma decisão oculta.
- `does_not_support` não exclui lugar verificado existente nem altera o provedor.
- O sinal não chama Google Places, não muda coordenadas e não substitui o
  extrator OpenAI.
- Sem `TYPESAFE_API_KEY`, o produto informa `unavailable` e mantém o contrato
  M1, sem inventar uma classificação.

## Fora de M2

- Login recuperável, contas sociais e recuperação de e-mail.
- Instagram como fluxo suportado de produto.
- Upload de mídia, scraping ou bypass de APIs oficiais.
- Worker, queue, Redis, microserviços, cobrança ou aplicativo nativo.
- Alegações de métricas de produção sem dados observados.
